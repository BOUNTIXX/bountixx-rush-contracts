# Testnet Delivery Plan

## Preconditions

- `cargo test` passes.
- `stellar contract build` produces a WASM artifact.
- A Testnet deployer account and a separate verifier account exist. Secret keys never enter the repository.
- The deployer funds its Testnet account through Stellar Friendbot or an approved Testnet faucet.

## First deployment sequence

1. Build `rush-vault` with `stellar contract build`.
2. Deploy the generated WASM to Stellar Testnet.
3. Initialize the deployed contract with an admin address and verifier address.
4. Use a Testnet asset contract to fund a small sponsor prize.
5. Settle only against a fixture result generated by `bountixx-rush-verifier`.
6. Record the contract ID and transaction links in a release note.

## Reproducible preflight

`scripts/deploy-testnet.ps1` builds the exact non-optimized artifact used for
the release, prints its SHA-256 hash and deployment configuration, and stops.
It cannot target Mainnet. It only submits deployment transactions when called
with both `-Execute` and `-Confirmation DEPLOY_TESTNET`.

```powershell
./scripts/deploy-testnet.ps1 \
  -AdminIdentity <secure-cli-identity-or-approved-signer> \
  -AdminAddress <G...admin-public-address> \
  -VerifierAddress <G...verifier-public-address>
```

Run the dry preflight first, then have an independent reviewer compare the
printed artifact hash with the release note before supplying `-Execute`.
The script never accepts a non-Testnet passphrase and never stores credentials.

## Safety

This repository does not authorize Mainnet deployment until independent review of the contract, result-attestation flow, expiry/refund path, access control, and operational key management.
